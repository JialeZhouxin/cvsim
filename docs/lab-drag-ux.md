# 拖拽式编程界面：用户视角的体验设计

> **一句话：** 用户不该"学会"你的拖拽界面，而该"本能地"用它。本文从**用户视角**描述一个对使用者最友好的拖拽式编程界面（以 Gaussian Lab 五线谱电路编辑器为具体场景），每一条设计主张都锚定 [Laws of UX](https://lawsofux.com/) 的对应法则。
> **配套：** 当前实现手册 [`lab-interaction.md`](./lab-interaction.md)（现状）、产品愿景 [`vision-gaussian-lab-ui.md`](./vision-gaussian-lab-ui.md)。
> **更新：** 2026-08-06

---

## 0. 用户是谁，一次会话想干什么

用户（研究者本人）坐在界面前的三个时刻：

| 时刻 | 内心问题 | 界面必须回答 |
|------|---------|-------------|
| 第一次打开 | "这怎么用？" | **不用教**，看得懂、拖得动 |
| 搭到一半 | "下一步放哪？" | 每个格子**预先可见**，落点**提前预告** |
| 出结果时 | "这个数可信吗？" | 数字与物理一致，**错了我能知道为什么** |

拖拽式编程的核心承诺：**把"编程"降级为"摆积木"**——思考物理，而不是思考语法。下面每一条法则都服务于这个承诺。

---

## 1. 感知与第一印象：让界面"看起来就会用"

### 1.1 Aesthetic-Usability Effect（美观-可用性效应）
> 用户倾向于认为**美观的设计更好用**，且更宽容其小瑕疵。

拖拽界面最容易"看起来难用"的地方：格子、轨道、门块的视觉噪声。理想状态：

- 空白画布是**安静的**——淡色格子线 + 留白，让用户一眼看到"这是可以放东西的棋盘"；
- 门块是**实体的**——有厚度、有圆角、有清晰的图标文字，拖起来像拿起一个真物件；
- 视觉统一性 > 装饰：同一操作（拖/点/滑）在界面各处长得一样。

### 1.2 Von Restorff Effect（冯·雷斯托夫效应）
> 视觉上与众不同的元素，最容易被记住。

**预览与高亮是界面里唯一"会动、会变色"的东西**，所以它们必须只属于"当前拖拽"这一个事件：

- 悬停格高亮（普通） vs 冲突格变红（危险）——**两种状态只用两种颜色**，红色绝不在其他场景出现；
- ghost 预览块是**半透明虚线**，与实心门块形成唯一对比——用户永远分得清"还没放"和"已放下"。

### 1.3 Law of Prägnanz（简洁法则）
> 人脑会把复杂图形简化成最简单的形态。

- 一列 = 一个格子（72px 宽、轨道线连贯）——用户看到的不是"坐标"，是"槽位"；
- 双模门跨两轨显示为一个连通块，而不是"两个门"；
- **拒绝用概念术语做标签**：格子上写"BS 0.5"，用户要看到"分束器 50/50"。

## 2. 选择与决策：别让用户做选择题

### 2.1 Hick's Law（希克定律）
> 决策时间随选项数量与复杂度增长。

拖拽式编程最容易违反它：把 20 种操作全堆进托盘。理想设计：

- **托盘白名单**：只放高频操作（≤ 9 个），低频操作进"更多…"折叠；
- **同类分组**：源/门/通道/测量四组，组间用分隔线（Common Region，见 §5.1）；
- 默认场景已经是一个完整电路——用户**永远从"能跑"开始**，而不是从空画布开始。

### 2.2 Choice Overload（选择过载）
> 选项太多导致决策瘫痪或满意度下降。

- 双模门第二步"选轨道 B"：可选项只剩轨道，且**第一步后只有目标轨道被武装高亮**——用户只需在 2-3 条里选 1 条；
- 参数编辑：每个门只暴露**该门的真实参数**（滑块范围贴合物理域），不是通用属性面板；
- 扫描面板同理：节点下拉只列"可扫"节点，参数只列"可扫"参数。

### 2.3 Miller's Law（米勒定律）
> 工作记忆约 7±2 个组块。

- 单次拖拽的"状态"：拖什么 + 放哪 + 会不会冲突 = 恰好 3 件事，且**全部可视化**（拖着的卡片 + 高亮格 + 红/蓝颜色），不占记忆；
- 双模两步放置把"一次放两格"拆成两次记忆负担最小的一步；
- 状态栏一次只说**一件事**，且是用户当前动作的直接结果。

### 2.4 Occam's Razor（奥卡姆剃刀）
> 最简单的解释/方案往往最好。

- **能拖就不点**，能点就不输入：位置靠拖（不用敲坐标），参数靠滑（不用敲数字）；
- JSON 文本域**默认折叠**——它是救生通道，不是主界面；
- 任何"看起来一样的操作"只保留一种路径：点击托盘 = 快速追加；拖拽 = 指定位置。两种路径结果一致，用户不需要记第三条。

### 2.5 Tesler's Law（特斯勒定律）
> 每个系统都有不可削减的复杂性，关键是把它藏在哪。

- 物理的复杂性（xxpp 约定、模式编号、直积展开）**全部藏进后端**，界面只说"轨道 0/1"；
- 必须暴露的复杂性（高级参数 nbar、JSON 手工改）**折叠到底层**：卡片不显示，JSON 区可展开——专家想用能找到，新手永远看不见。

## 3. 目标与记忆：让用户随时知道"我在哪、下一步是什么"

### 3.1 Goal-Gradient Effect（目标梯度效应）
> 离目标越近，动力越强。

- 双模放置：状态栏提示"选择第二个模式（当前 mode A）"——用户知道**只差一步**，不会中途放弃；
- 空列可见（§5.2 反向应用）：画布总是显示"前方还有空格"，暗示"可以继续摆"；
- 扫描曲线从第一个点就开始画（边算边出点），而不是等全部算完——进度本身就是动力。

### 3.2 Zeigarnik Effect（蔡格尼克效应）
> 未完成的任务比已完成的任务更占据心智。

利用 + 防范双向用：

- **利用**：双模放置一旦武装，目标轨道保持高亮直到完成或显式取消——"悬而未决"的状态在界面上有实体形态，用户不会忘记自己在干嘛；
- **防范**：任何被拒绝的操作必须**说清为什么**（"该格已被占用（mode 1 @ x 5）"），否则"没放进去"会成为悬在心头的未完成任务，用户会反复尝试同一失败操作。

### 3.3 Serial Position Effect（序列位置效应）
> 列表首尾元素最容易被记住。

- 托盘把**最常用的操作放在首尾**（第一位 = 最常用源/门，末位 = 测量/重置），中间放次常用；
- 状态栏固定位置（底部）——用户知道去哪里看反馈，不看也会瞟到。

### 3.4 Jakob's Law（雅各布定律）
> 用户把其他软件的交互习惯带进来。

拖拽编程界的"通用语"：

- 拖 = 移动/放置、× = 删除、滑块 = 参数、滚动 = 查看更多——**全部沿用桌面系统惯例**，不发明新手势；
- 放下后格子上出现实心块（像文件管理器里的图标）、拖出画布外松手 = 取消（像取消拖动文件）——符合肌肉记忆；
- 颜色语义也借用惯例：红 = 错误/冲突，绿/蓝 = 有效，灰 = 不可用。

## 4. 交互与反馈：每一次拖拽都要被"接住"

### 4.1 Fitts's Law（菲茨定律）
> 目标越小、越远，到达越慢。

- **门块/托盘卡片 ≥ 44×44px**（触控级命中区），删除按钮 × 放大到 ≥ 24px 且悬停时扩大；
- **拖放目标 = 整格**（72px）而不是门中心——落点命中面积最大化；
- 删除按钮**悬停门才出现**（省空间）但出现即大——不牺牲命中率；
- 画布**横向滚动**代替缩小画布：内容多时用户滚动（顺手）而不是眯眼找小格子。

### 4.2 Doherty Threshold（多赫蒂阈值）
> 系统在 400ms 内响应，用户才会保持"心流"。

拖拽界面是心流密集区，各环节预算：

| 环节 | 预算 | 实现 |
|------|------|------|
| 悬停高亮/预览 | **即时**（< 16ms，纯 CSS 类切换） | 不做任何等待逻辑 |
| 拖放落定 | 即时（前端本地状态） | 不需要等后端 |
| 参数拖动 | **≤ 400ms** 防抖后出图 | 右栏 Wigner 防抖刷新 |
| 运行结果 | ≤ 500ms（小电路） | 后端 /run + 防抖合并 |
| 错误反馈 | 即时 | 拒绝 = 前端本地判定，不等 422 |

**关键**：冲突判定必须在**放下之前**（悬停时）完成——用户不该拖到终点才被告知失败。

### 4.3 Postel's Law（波斯特尔法则）
> 宽进严出：对自己严格，对用户宽容。

- **输入宽容**：JSON 里丢 `ui.x` 也能载入（自动补列）；拖放落点不在格中心也吸附；参数越界自动钳制到物理域；
- **输出严格**：后端校验所有输入（模式越界、门后插源 → 422），前端冻结图形并报错，绝不静默接受；
- 拖拽事件宽容：拖到轨道缝隙、拖到源区、中途松开——全部有定义的行为（吸附/忽略/取消），没有"卡住"。

### 4.4 Peak-End Rule（峰终定律）
> 用户对体验的记忆 = 高峰时刻 + 结束时刻。

拖拽界面的两个记忆点：

- **高峰**：放置成功的"咔嗒感"——格子高亮 → 放下 → 门块实心落定 + 状态栏 `ok`。这个瞬间要干脆、确定；
- **终点**：每次会话的结束 = 用户看到可信的数字（`ok · 384 ms` + 仪表读数）。结束态必须是**成功的、完整的**——所以默认场景保证"打开就能跑出结果"。

## 5. 布局与结构：视觉组织即认知组织

### 5.1 Law of Common Region（共同区域法则）
> 同区域内的元素被认为是一组。

- 托盘卡片**共用一个圆角容器**（而不是散落按钮）——一眼知道"这些都是一种东西"；
- 状态栏固定在底部条带，与画布分离——"这里是反馈区"无需解释；
- 参数卡片浮在门旁但**有边框+阴影**——是"从门弹出的东西"，不是画布的一部分。

### 5.2 Law of Proximity（接近法则）
> 靠近的元素被认为相关。

- **门块贴在自己的格子里**（间隙小），离相邻格的门远——用户用眼睛就能数"这是第几列"；
- ghost 预览块**与目标格重合**（而不是跟在鼠标旁）——"将要在这里"的语义靠位置表达；
- 源参数（r/α）显示在源块上，门参数在卡片里——信息与它的归属对象贴近。

### 5.3 Law of Similarity（相似性法则）
> 相似的元素被认为同类。

- 所有门块同一形态（同尺寸同圆角），**只靠图标+文字区分类型**——"它们是一类东西"；
- 双模门与单模门在形态上只是"宽度"差异，用户理解"更宽 = 占两格"；
- 危险/冲突统一红色，预览统一虚线——形态编码全局一致，不换肤。

### 5.4 Law of Uniform Connectedness（统一连通法则）
> 视觉连通的元素被认为一体。

- 双模门的**两个端块用同色连线连接**（或一个连续块）——用户立刻知道"这是一个器件占两格"，而不是两个门；
- 源区 → 轨道：源块与该轨道在视觉上**对齐**（同一水平线）——"这个光从这条轨道进"；
- 选中/悬停态：门块 + 其参数卡片同色描边——"卡片属于这个门"。

### 5.5 Parkinson's Law（帕金森定律）
> 任务会膨胀到占满可用时间——界面亦然：内容会膨胀到占满可用空间。

- 画布格子**无限延伸但只画需要的宽度**（当前最右门 + 固定余量）——空白不被"占满"的冲动污染，用户总有清晰的落点；
- 托盘**保持一行/一列紧凑**，不随内容变高——复杂度守恒在折叠里（§2.5）。

## 6. 理想交互流（用户视角全旅程）

```
打开页面
 └─ 看到：默认电路已经摆好（2 轨 + 2 位移器），状态栏 ok，右栏有 Wigner 图   ← 从能跑的开始（Hick §2.1）
     1. 拖一个压缩器到轨道 0 的空白格
        ├─ 悬停：格子高亮 + 虚线预览 `压缩 ?`                              ← 提前预告（Doherty §4.2）
        ├─ 被占格：变红 —— 不用放下就知道                                  ← 冲突前置（Von Restorff §1.2）
        └─ 放下：实心落定，状态栏 ok
     2. 拖分束器到轨道 0 第 3 格
        ├─ 状态栏："选择第二个模式（当前 mode 0）" + 轨道 0 武装             ← 差一步（Goal-Gradient §3.1）
        └─ 点击轨道 1 → 落定，跨两轨的连通块出现                           ← 一步到位（Uniform Connected §5.4）
     3. 想改分束器比例：点门 → 滑块 0.5 → 拖到 0.7
        └─ 右栏 Wigner 图 400ms 内变化                                    ← 心流（Doherty §4.2）
     4. 拖错了：拖回格子的门到别的格，被占格红色拒绝，门留在原位             ← 零损失（Peak-End §4.4）
     5. 完成：右栏读出光子数/纯度，状态栏 ok · 384 ms
        └─ 满意地关掉 —— 结尾是"可信的数字"                               ← 峰终（§4.4）
```

**全程用户一次都不需要**：读文档、敲坐标、数模式编号、猜为什么失败。

## 7. 与当前 Gaussian Lab 实现的差距对照

| 法则 | 当前状态 | 差距 / 建议 |
|------|---------|------------|
| Hick's / Choice Overload | 托盘白名单 ≤ 8 项 ✓ | 建议按"源/门/通道/测量"分组加分隔线 |
| Von Restorff | 冲突红显 + ghost 虚线 ✓ | — |
| Doherty | 悬停即时、放置即时、运行防抖 ✓ | 参数滑块→右栏刷新的 400ms 已达标 ✓ |
| Fitts's | 格 = 72px 命中区 ✓；删除 × 偏小 | 建议 × 命中区 ≥ 24px（现约 16px） |
| Goal-Gradient | 双模状态栏引导 ✓ | 可在目标轨道上再加"→ 点击"微文案 |
| Zeigarnik | 拒绝必给原因 ✓ | — |
| Postel's | legacy JSON 宽容 ✓、后端严格 ✓ | — |
| Peak-End | 默认场景开箱能跑 ✓ | — |
| Prägnanz | 双模连通块 ✓ | — |
| Miller's | 双模两步拆分 ✓ | — |
| 空白画布 | 初始 ≥ 10 空列 ✓ | — |

**结论：L5.5 格子化已覆盖大部分法则；最大剩余差距是 Fitts（删除按钮命中区）与 Hick（托盘分组）。**

- [ ] 我从没收到过没有原因的错误
